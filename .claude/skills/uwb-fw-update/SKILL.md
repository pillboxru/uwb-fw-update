# uwb-fw-update — массовое обновление прошивок WB

Утилита неофициальная: Wiren Board её не разрабатывает и не поддерживает. Если пользователь спрашивает, куда обращаться с проблемами утилиты, — не в техподдержку Wiren Board.

Обновление прошивки может вывести устройство из строя; пользователь делает это на свой страх и риск, автор утилиты за вред не отвечает. Перед первым `update` или `recover` напомните об этом пользователю вместе с вопросом о разрешении.

Утилита работает **на контроллере**. Агент управляет ей по SSH: запускает прогон в фоне, опрашивает состояние в JSON, читает отчёт и разбирает проблемы.

Подключение к контроллеру (поиск по mDNS, `BatchMode=yes`, `sshpass`) — по правилам скилла **wb-plc:wiren-board**. Диагностика шины, которая не связана с прошивкой (CRC, таймауты, шаблоны), — **wb-plc:wb-serial**. Ниже `<HOST>` — адрес контроллера, а `WFU` — путь к утилите:

```bash
WFU=/mnt/data/uwb-fw-update/uwb-fw-update     # не в PATH, всегда полный путь
ssh -o BatchMode=yes root@<HOST> "$WFU --version"
```

В Git Bash на Windows нет `sshpass`. Если вход по ключу не работает, попросите пользователя настроить ключ (`ssh-copy-id`). Пароль в файлах не сохраняйте.

## Почему здесь нужна осторожность

Прогон не просто читает данные, а меняет объект:

- **Режим `direct` (по умолчанию) останавливает `wb-mqtt-serial` на весь прогон.** Даже `check` в этом режиме его останавливает. Пока драйвер стоит, автоматика объекта не работает: свет, климат, насосы. Одна только остановка драйвера занимает около 25 с.
- **Прошивка на время записи выводит устройство из работы.** Если запись прервётся, устройство останется в загрузчике, пока его не восстановят.
- **Обновление загрузчика через шлюз** — единственная операция с реальным риском «кирпича»: сбой питания устройства в окне около 100 мс.
- **У WB-MSW и WB-MIR прошивка стирает сохранённые ИК-команды.**

Поэтому действуйте так. Всё, что только читает (`list`, `status`, `report`, `logs`, `runs`, `cache list`), выполняйте свободно. Перед `update`, `recover`, `check --access direct`, `stop`, `--force*` и `--allow-downgrade` покажите пользователю план и получите явное согласие. План — это какие шины и устройства затронуты, какой режим доступа, остановится ли драйвер, примерная длительность. «Проверь версии» — это согласие только на проверку, а не на прошивку.

## Выбор инструмента

- **uwb-fw-update** — много устройств, целый шлюз или объект, устройства за WB-MGE/WB-MIO-E, нужны отчёт по каждому устройству и продолжение прерванного прогона. Также если пользователь сам назвал утилиту или она уже лежит в `/mnt/data/uwb-fw-update/`.
- **`wb-cli serial wb-fw`** (см. wb-plc:wb-serial) — одно-два устройства, когда uwb-fw-update на контроллере нет, а ставить его пользователь не хочет.
- **Нельзя запускать одновременно** uwb-fw-update, `wb-mcu-fw-updater`, обновление из веб-интерфейса и `wb-cli serial wb-fw`. Блокировку учитывает только сама утилита, остальные средства её не видят, и на одной шине получится два мастера.

## Установка (если `$WFU --version` не отвечает)

Утилита — один файл (zipapp, около 50 КБ), ей нужен только штатный `python3`. Готовый файл лежит в релизах GitHub: если у контроллера есть интернет, скачайте его прямо туда:

```bash
ssh root@<HOST> 'mkdir -p /mnt/data/uwb-fw-update && curl -fL -o /mnt/data/uwb-fw-update/uwb-fw-update https://github.com/pillboxru/uwb-fw-update/releases/latest/download/uwb-fw-update && chmod +x /mnt/data/uwb-fw-update/uwb-fw-update && /mnt/data/uwb-fw-update/uwb-fw-update --version'
```

Иначе файл собирается из репозитория утилиты командой `python tools/build.py`, результат — `uwb-fw-update` в корне репозитория (он же лежит в git готовым), и копируется по scp:

```bash
ssh root@<HOST> 'mkdir -p /mnt/data/uwb-fw-update'
scp uwb-fw-update root@<HOST>:/mnt/data/uwb-fw-update/uwb-fw-update
ssh root@<HOST> 'chmod +x /mnt/data/uwb-fw-update/uwb-fw-update && /mnt/data/uwb-fw-update/uwb-fw-update --version'
```

**Обновление самой утилиты.** `$WFU version --check --json` — только чтение, выполняйте свободно (поле `update_available`). Если `check`/`update` пишут «Доступна новая версия uwb-fw-update», сообщите пользователю. `$WFU self-update -y` меняет только файл утилиты (прежний — `uwb-fw-update.prev`), устройства и `wb-mqtt-serial` не трогает, во время прогона отказывает; всё равно выполняйте его только с согласия пользователя.

Каталог `/mnt/data/uwb-fw-update/` переживает обновление прошивки контроллера. Кроме утилиты, там лежат `cache/`, `devices.json` и `runs/<run-id>/`.

## Основной сценарий

### 1. Что будет обработано

```bash
ssh root@<HOST> "$WFU list --json"
```

Список берётся из `/etc/wb-mqtt-serial.conf`. У каждого устройства есть `bus_key`, `slave`, `device_type`, `label`, а у пропущенных — `skip_reason`. Покажите пользователю сводку по шинам: сколько устройств будет обработано, сколько пропущено и почему.

Фильтры одинаковы для `list`, `check`, `update`, `recover` и `cache sync`:

```
--port /dev/ttyRS485-1       локальная шина
--port 192.168.1.24:23      один порт шлюза
--port 192.168.1.21         все порты шлюза
--slave 34                   вместе с --port — одно устройство (повторяемо)
--device-id <id|name>        по конфигурации
```

### 2. Выбор режима доступа

```bash
ssh root@<HOST> 'systemctl is-active wb-mqtt-serial'
```

| режим | когда | цена |
|---|---|---|
| `--access rpc` | драйвер запущен, автоматику останавливать нельзя | запись в 2–3 раза медленнее; драйвер пишет ошибки опроса прошиваемого устройства, пока оно в загрузчике (это нормально) |
| `--access direct` | окно обслуживания, нужна скорость, драйвер уже остановлен | автоматика стоит весь прогон |
| `--access auto` | не знаете заранее | `rpc`, если драйвер жив и RPC `port/Load` объявлен, иначе `direct` |

Для `check` почти всегда подходит `--access rpc`: так проверка ничего не останавливает. Она проверена на железе на 152 устройствах за 91 с. Если `rpc` недоступен, утилита выходит с кодом 3 и к шинам не обращается. Тогда объясните пользователю, что остаётся только `direct` с остановкой драйвера, и спросите согласия.

### 3. Проверка версий

```bash
ssh root@<HOST> "$WFU check --access rpc --detach"      # + фильтры
```

Дальше опрос (шаг 5), затем отчёт. Статусы `update_available`, `up_to_date` и `in_bootloader` — это и есть план обновления. Покажите пользователю, что и на какие версии обновится. Если у устройства есть обновление загрузчика и оно стоит за шлюзом, скажите об этом отдельно (риск см. выше).

Сеть на контроллере может быть нестабильной, а прошивки лучше скачать заранее:

```bash
ssh root@<HOST> "$WFU cache sync"          # после check: знает сигнатуры устройств
```

### 4. Обновление (только после согласия)

```bash
ssh root@<HOST> "$WFU update --access rpc --detach -y"   # + фильтры и флаги
```

Всегда передавайте `--detach -y`. `-y` снимает вопрос «Начать обновление?», который задаёт только `update`. `check` и `recover` ничего не спрашивают, им достаточно `--detach`. Без `--detach` консоль переходит в живой просмотр до конца прогона, а это десятки минут, и SSH-вызов агента повиснет или упрётся в таймаут. Прогон идёт как transient unit systemd `uwb-fw-update-<run-id>` и не зависит от SSH-сессии. Номер прогона выводится в строке `прогон <run-id> запущен в фоне`.

Полезные флаги:

| флаг | зачем |
|---|---|
| `--no-bootloader` | только прошивки; при ненадёжной линии или шлюзе без резервного питания |
| `--jobs N` | шин параллельно (по умолчанию 4). Устройства внутри одной шины всегда идут по очереди |
| `--offline` | только кэш |
| `--force` | перезаписать ту же версию прошивки (восстановление, эксперимент) |
| `--force-bootloader` | перезаписать загрузчик той же версии — только по прямой просьбе |
| `--allow-downgrade` | откат на версию из релиза |
| `--suite testing` | другой канал релизов |
| `--trace` | hex-кадры Modbus в лог шины (для разбора проблем) |

**Порядок на новом объекте:** сначала одно устройство на локальном порту, затем одно за шлюзом, потом целый шлюз и только после этого всё. Предложите этот порядок, если утилиту на объекте ещё не запускали.

Ориентиры по времени: в `direct` устройство занимает 10–60 с (на 9600 бод дольше), в `rpc` в 2–3 раза больше. Полный объект из 157 устройств на 20 шинах с `--jobs 20` занял 47 минут.

### 5. Наблюдение

```bash
ssh root@<HOST> "$WFU status --json"          # последний прогон; --run <id> — конкретный
```

Поля: `run_id`, `mode`, `status`, `total`, `counters` (статус → число), `buses{<шина>: {status, device, stage, ...}}` и `control` (пауза и остановки). Прогон завершён, когда `status` принимает одно из значений `finished`, `cancelled`, `failed`, `crashed`, `refused`. Если к статусу приписано «процесс не найден», воркер умер: см. `references/troubleshooting.md`.

Опрашивайте раз в 30–60 с и не чаще: запись одного устройства длится десятки секунд. Пользователю сообщайте прогресс кратко: «обработано 40/157, проблем 1, идёт шина X».

Если нужны подробности по шине:

```bash
ssh root@<HOST> "$WFU logs --bus 192.168.1.24:23 | tail -50"
ssh root@<HOST> "$WFU logs | tail -50"           # общий журнал прогона
```

Не используйте `watch` и `logs -f`: это интерактивные и бесконечные команды для человека.

### 6. Отчёт

```bash
ssh root@<HOST> "$WFU report --json"                  # код выхода 1 = есть проблемы
ssh root@<HOST> "$WFU report --failed-only"           # человекочитаемо, с подсказками
```

В JSON есть `ok`, `counts` и `devices[]`. У каждого элемента: `bus`, `slave`, `label`, `model`, `status`, `reason`, `code` (например `failed:jump:tcp_requires_131_or_9600`), `ok`, `message`, `fw_before`, `fw_after`, `fw_target`, `bl_*`, `notes`.

Итог для пользователя: сколько устройств обновлено, сколько уже были актуальны, сколько пропущено. Проблемные устройства перечислите поимённо — шина, адрес, модель, причина — с рекомендацией по каждому из `references/troubleshooting.md`. Отдельно выделите `stuck_in_bootloader` и `interrupted`: эти устройства сейчас не работают.

## Управление идущим прогоном

| задача | команда |
|---|---|
| мягко остановить: текущие устройства доводятся, новые не начинаются | `$WFU stop` |
| остановить одну шину | `$WFU stop --bus <шина>` |
| быстро: запись прошивки прерывается между блоками, загрузчик всегда дописывается | `$WFU stop --now -y` |
| пауза и продолжение | `$WFU pause` / `$WFU resume` |
| продолжить остановленный или прерванный прогон | `$WFU update --resume <run-id> --detach -y` |
| только восстановить прерванные устройства | `$WFU recover --from-run <run-id> --detach` |
| список прогонов | `$WFU runs` |

Не останавливайте прогон через `kill -9`, перезагрузку контроллера или `systemctl stop wb-mqtt-serial`. Утилита переживёт это (устройства восстанавливаются), но потом их придётся восстанавливать отдельно. `stop --now` делает то же самое аккуратно.

Пауза в режиме `direct` держит драйвер остановленным. Через 30 минут (`--pause-timeout`) она сама превращается в мягкую остановку.

## Коды выхода

`0` — все устройства в порядке. `1` — есть проблемные устройства. `2` — ошибка параметров или отказ в подтверждении. `3` — ошибка окружения: нет root, уже идёт другой прогон, недоступен RPC или конфиг, нет сети.

Код 3 с текстом «уже выполняется прогон» не повод запускать заново. Посмотрите `status --json`: вероятно, прогон запустил другой администратор.

## Проблемы и восстановление

Разбор каждого `failed:*`, `stuck_in_bootloader:*`, `interrupted:*` и `skipped:*`, аварийного прогона (`crashed`), устройства, которое не отвечает после обновления загрузчика, а также ограничения шлюзов — в **`references/troubleshooting.md`**. Прочитайте его, как только в отчёте появилось что-то кроме `updated`, `recovered`, `up_to_date` и штатных пропусков по конфигурации.

Полное описание утилиты — `README.md` в её репозитории. Справка на контроллере — `$WFU --help` и `$WFU <команда> --help`.
