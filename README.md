# uwb-fw-update — массовое обновление прошивок устройств Wiren Board

> **Неофициальное приложение.** `uwb-fw-update` (буква «u» — unofficial) не разрабатывается и не поддерживается компанией Wiren Board. С вопросами по утилите не обращайтесь в техподдержку Wiren Board; штатные средства обновления — `wb-mcu-fw-updater` и веб-интерфейс контроллера.

> [!WARNING]
> **Обновление прошивки — опасная процедура.** Сбой питания, помехи или обрыв связи во время записи, ошибка в прошивке или в утилите могут вывести устройство из строя. Устройство может перестать работать и потребовать восстановления или ремонта. На время обновления объект остаётся без управления этими устройствами.
>
> Вы используете утилиту **на свой страх и риск**. Автор не несёт ответственности за использование программы и за любой вред, причинённый ею устройствам, оборудованию, объекту или данным. Программа предоставляется «как есть», без каких-либо гарантий (см. [лицензию MIT](LICENSE)).

Утилита обновляет загрузчики и прошивки Modbus-устройств Wiren Board, подключённых:

- напрямую к контроллеру — `/dev/ttyRS485-*`, `/dev/ttyMOD*`;
- через шлюзы WB-MGE v2/v3 и WB-MIO-E — порты `port_type: "tcp"` в `wb-mqtt-serial.conf` (Modbus RTU поверх TCP, режим «TCP Server» / «прозрачный мост»).

Основные возможности:

- **Список устройств** берётся из `/etc/wb-mqtt-serial.conf`. Отключённые порты и устройства, модули WBIO (`247:1`), `modbus tcp` и не-Modbus протоколы пропускаются, у каждого пропуска указана причина.
- **Версии прошивок** выбираются по релизу контроллера: `SUITE` из `/usr/lib/wb-release`, индексы `release-versions.yaml` — так же, как у `wb-mcu-fw-updater` и `wb-mqtt-serial`.
- **Порядок обновления:** сначала загрузчик (если устарел), затем прошивка, затем проверка версий.
- **Восстановление:** устройства, найденные в загрузчике или «застрявшие» после сбоя записи, восстанавливаются автоматически.
- **Параллельность:** шины обрабатываются одновременно, устройства внутри шины — строго по очереди.
- **Логи:** отдельный лог для каждой шины, общий журнал событий и итоговый отчёт: что не обновилось, где и почему.
- **Локальный кэш** прошивок; md5 проверяется по ETag сервера.
- **Фоновый режим:** прогон выполняется под systemd и не зависит от SSH-сессии. Консоль нужна только для просмотра и управления, к прогону можно переподключаться.
- **Ручная остановка:** мягкая, быстрая, отдельной шины; пауза; продолжение остановленного прогона.
- **Без остановки `wb-mqtt-serial`** (`--access rpc`): обмен идёт через RPC `port/Load` самого драйвера, автоматика объекта продолжает работать. Пока режим проверяется, по умолчанию используется прямой доступ с остановкой драйвера.

## Установка на контроллер

Утилита собирается в **один исполняемый файл** (zipapp, около 50 КБ). Нужен только штатный `python3` контроллера.
Готовый файл публикуется в [релизах на GitHub](https://github.com/pillboxru/uwb-fw-update/releases) — его можно скачать прямо на контроллер:

```sh
mkdir -p /mnt/data/uwb-fw-update
curl -fL -o /mnt/data/uwb-fw-update/uwb-fw-update     https://github.com/pillboxru/uwb-fw-update/releases/latest/download/uwb-fw-update
chmod +x /mnt/data/uwb-fw-update/uwb-fw-update
/mnt/data/uwb-fw-update/uwb-fw-update --version
```

Или собрать самому и скопировать:

```sh
# на компьютере разработчика
python tools/build.py                                  # -> ./uwb-fw-update
scp uwb-fw-update root@<контроллер>:/mnt/data/uwb-fw-update/uwb-fw-update
# на контроллере
chmod +x /mnt/data/uwb-fw-update/uwb-fw-update
/mnt/data/uwb-fw-update/uwb-fw-update --help
```

Всё, что относится к утилите, лежит в одном каталоге `/mnt/data/uwb-fw-update/` на разделе данных — он переживает обновление прошивки контроллера. Чтобы обновить утилиту, достаточно заменить файл `uwb-fw-update` (или выполнить `uwb-fw-update self-update`, см. ниже). Работать из исходников тоже можно: `PYTHONPATH=<каталог с uwbfwup> python3 -m uwbfwup <команда>`.

### Права

- **Нужен root:** `check`, `update`, `recover`, `stop`, `pause`, `resume`, `cache sync`, `cache prune`, `prune-runs`, `self-update`. Эти команды останавливают `wb-mqtt-serial` (в режиме `direct`), работают с портами RS-485 и шлюзами, создают службу systemd, пишут в каталог данных и управляют воркером, который запущен от root. Без прав root команда сразу выходит с понятным сообщением (код 3), ничего не трогая.
- **Доступно любому пользователю:** `list`, `status`, `watch`, `report`, `logs`, `runs`, `cache list`, `cache verify`, `version`. Файлы состояния и отчётов записываются с правами 0644.

### Одновременный запуск

Одновременно может работать только один прогон, даже если его запускают разные администраторы из разных консолей. Это гарантирует блокировка `/run/lock/uwb-fw-update.lock`, которую держит воркер.

- **Второй запуск** (`check`/`update`/`recover`) отказывает сразу, до остановки `wb-mqtt-serial`: «уже выполняется другой прогон». Код выхода 3.
- **Если два запуска стартовали в одну и ту же секунду,** блокировку получит один воркер. Второй ничего не трогает и помечает свой прогон как `refused` («к шинам не обращались»). Номера прогонов не пересекаются.
- **Управлять идущим прогоном может любой root:** `watch`, `status`, `stop`, `pause`. Команды управления из разных консолей упорядочиваются.
- **Если кто-то вручную запустит `wb-mqtt-serial` во время прогона,** утилита заметит это в течение 5 с. Новые устройства она не начинает, прогон мягко останавливает и пишет предупреждение в журнал. С администратором утилита не спорит, драйвер обратно не останавливает.
- **Сторонние средства обновления** (`wb-mcu-fw-updater`, обновление из веб-интерфейса) блокировку не учитывают. Не запускайте их одновременно с утилитой.

Зависимости уже есть на контроллере: `python3`, `python3-serial`. `python3-yaml` необязателен — без него используется встроенный разборщик индексов.

Каталог утилиты — `/mnt/data/uwb-fw-update/` (каталог данных переопределяется `--home` или `UWBFWUP_HOME`):

| путь | что |
|---|---|
| `uwb-fw-update` | сама утилита (единый файл) |
| `cache/` | индексы релизов и файлы `.wbfw` с метаданными (size, md5, ETag) |
| `selfcheck.json` | последняя версия утилиты на GitHub и время проверки |
| `devices.json` | последние известные сигнатуры и версии устройств; нужна для восстановления старых загрузчиков, не сообщающих сигнатуру |
| `runs/<run-id>/` | прогон: `state.json`, `events.jsonl`, `report.json`, `run.log`, `bus-<шина>.log`, `control.json` |

### Обновление утилиты

```sh
uwb-fw-update version --check [--json]   # установленная и последняя версия на GitHub
uwb-fw-update self-update [-y]           # скачать последний релиз и заменить файл утилиты
uwb-fw-update self-update --check-only   # только проверить
```

`self-update` скачивает файл из последнего релиза GitHub, сверяет sha256, проверяет, что это собранная утилита и что она сообщает ожидаемую версию, и атомарно заменяет запущенный файл. Прежняя версия сохраняется рядом как `uwb-fw-update.prev`. Во время прогона `self-update` отказывает. Устройства и `wb-mqtt-serial` он не трогает.

Команды `check`, `update` и `recover` при запуске напоминают одной строкой, если на GitHub есть более новая версия. На GitHub утилита обращается не чаще раза в сутки (результат хранится в `selfcheck.json` каталога данных), при недоступности сети молчит; с `--offline` или переменной `UWBFWUP_NO_UPDATE_CHECK=1` не проверяет вовсе.

## Быстрый старт

```sh
uwb-fw-update list                          # что будет обработано (по конфигурации)
uwb-fw-update check                         # опросить устройства и сравнить версии, ничего не прошивая
uwb-fw-update cache sync                    # заранее скачать нужные прошивки
uwb-fw-update update                        # обновить всё (в фоне + живой просмотр)
uwb-fw-update report --failed-only          # что не обновилось и почему
```

Выбор устройств (работает для `list`, `check`, `update`, `recover`, `cache sync`):

```sh
--port /dev/ttyRS485-1          # локальная шина
--port 192.168.1.24:23         # один порт шлюза
--port 192.168.1.21            # все порты шлюза (502 и 503 у WB-MGE v3)
--slave 34                      # вместе с --port — одно устройство; повторяемо
--device-id <id|name>           # по id/name из конфигурации
```

Примеры:

```sh
uwb-fw-update update --port /dev/ttyRS485-1 --slave 131       # одно устройство
uwb-fw-update update --port 192.168.1.24:23                  # один шлюз
uwb-fw-update update --jobs 8 --no-bootloader                 # только прошивки, 8 шин параллельно
uwb-fw-update recover --port 192.168.1.25                    # только восстановить застрявшие в загрузчике
```

Параметры `update`:

| флаг | назначение |
|---|---|
| `--no-bootloader` / `--fw-only` | не обновлять загрузчики |
| `--force-bootloader` | перезаписать загрузчик той же версии (например, для восстановления); сразу после него записывается прошивка |
| `--force` | перезаписать прошивку той же версии (загрузчик `--force` не затрагивает) |
| `--allow-downgrade` | разрешить откат на версию из релиза |
| `--suite testing` | другой канал релизов |
| `--offline` | только локальный кэш |
| `--jobs N` | число параллельных шин (по умолчанию 4) |
| `--trace` | hex-кадры Modbus в лог шины |
| `--access direct\|rpc\|auto` | доступ к шинам (см. «Режимы доступа к шинам»); по умолчанию `direct` |
| `--mqtt HOST[:PORT]` | MQTT-брокер для режима `rpc` (по умолчанию `localhost:1883`) |
| `--no-stop-serial` | `direct`: не останавливать `wb-mqtt-serial` (если вы остановили его сами) |
| `--foreground` | выполнять в текущей консоли (для отладки; закрытие консоли прервёт прогон) |
| `--detach` | запустить в фоне и сразу выйти |
| `-y` | не спрашивать подтверждение |

## Режимы доступа к шинам

| режим | как работает | `wb-mqtt-serial` |
|---|---|---|
| `direct` (по умолчанию) | утилита сама открывает `/dev/ttyRS485-*` и TCP-порты шлюзов | остановлен на весь прогон |
| `rpc` | каждый запрос Modbus — вызов RPC `wb-mqtt-serial/port/Load` (`protocol: "raw"`) через MQTT; драйвер выполняет его в своей очереди между опросами устройств | работает, автоматика не прерывается |
| `auto` | `rpc`, если драйвер запущен и RPC `port/Load` объявлен; иначе `direct` | зависит от выбора |

Особенности `rpc`:

- **Параметры линии локального порта** (скорость, чётность, стоп-биты) передаются в каждом запросе и действуют только на него. Поэтому переход через рег. 129 и поиск загрузчика на 9600 8N2 работают, а остальные устройства шины драйвер продолжает опрашивать на рабочих настройках.
- **Шлюзы:** используется соединение, которое уже держит драйвер. WB-MGE v3 («прозрачный мост», один мастер) не требует остановки драйвера.
- **Скорость:** между нашими кадрами драйвер опрашивает остальные устройства шины, плюс задержка MQTT. Запись прошивки в 2–3 раза медленнее, чем в `direct` (на железе: WB-MWAC 273 блока — 25 с против 9 с; WB-M1W2 на 9600 — 107 с против 48 с). После каждого ответа драйвер выжидает паузу «конец кадра» (`frame_timeout`), даже если все байты получены, поэтому она задана минимальной: 20 мс для локального порта, 30 мс для шлюза. Минимальный таймаут ответа у драйвера — 500 мс, поэтому молчащие устройства проверяются дольше.
- **Прошиваемое устройство драйвер тоже опрашивает.** Пока оно в загрузчике, в журнале драйвера будут ошибки опроса по этому устройству. После старта прошивки драйвер сам переподключает его и записывает параметры из шаблона. Тот же подход (покадровый `port/Load`) используют wb-mcu-fw-updater и wb-device-manager.
- **Пауза** не ограничена по времени: драйвер работает, `--pause-timeout` не действует.
- **Если `wb-mqtt-serial` остановят во время прогона,** утилита заметит это в течение 5 с и мягко остановит прогон: обмен через RPC больше некому выполнять.
- **Если драйвер сам обновляет устройства** (веб-интерфейс), при старте прогона выводится предупреждение.
- Брокер без авторизации на `localhost:1883` (штатная настройка контроллера); другой адрес — `--mqtt`.
- `--access rpc` при недоступном драйвере или RPC завершается с кодом 3, к шинам не обращаясь.

## Фоновый режим и просмотр

`update`, `check` и `recover` сначала выполняют быструю проверку в консоли: разбирают конфиг и применяют фильтры. Затем прогон запускается как transient unit systemd `uwb-fw-update-<run-id>`, а консоль переходит в `watch`.

- Закрытие SSH-сессии или терминала на прогон не влияет.
- `uwb-fw-update watch` возвращает к просмотру текущего прогона и показывает, сколько событий пропущено. `--from-start` выводит журнал целиком.
- `q` или `Ctrl+C` в `watch` — выход **только из просмотра**.
- `uwb-fw-update status`, `uwb-fw-update logs [--bus <шина>] [-f]`, `journalctl -u uwb-fw-update-<run-id>` — дополнительные способы смотреть за ходом.
- **Гарантированный запуск драйвера.** В режиме `direct` `wb-mqtt-serial` останавливается на время прогона. Обратно его запускает сам воркер, а если воркер упал или убит (`kill -9`), драйвер поднимает `ExecStopPost` юнита.
- **Аварийное завершение.** Если прогон завершился аварийно (питание, OOM), следующий запуск это обнаружит. Он покажет устройства, которые прошивались в момент сбоя, и добавит их в новый прогон для проверки и восстановления.

## Ручная остановка

Управлять прогоном можно из любой консоли:

| команда | действие |
|---|---|
| `uwb-fw-update stop` | мягкая остановка: текущие устройства доводятся до конца, новые не начинаются |
| `uwb-fw-update stop --bus 192.168.1.24:23` | то же для одной шины, остальные продолжают |
| `uwb-fw-update stop --now` | быстрая: запись **прошивки** прерывается между блоками (устройство остаётся в загрузчике, это безопасно и восстанавливаемо). Запись **загрузчика** не прерывается никогда: шина остановится после загрузчика и следующей за ним прошивки |
| `uwb-fw-update pause` / `resume` | пауза перед следующими устройствами |
| `systemctl stop uwb-fw-update-<id>` | равносильно `stop --now` |
| в `watch`: `s` / `S` / `p` | мягкая остановка / быстрая остановка / пауза (с подтверждением) |

**Пауза ограничена по времени** (режим `direct`). На паузе `wb-mqtt-serial` остановлен, и автоматика объекта не работает. Поэтому пауза дольше 30 минут автоматически превращается в мягкую остановку: драйвер запускается, оставшиеся устройства получают статус `cancelled` и доступны для `--resume`. `watch` показывает обратный отсчёт. Предел задаётся `--pause-timeout MIN`, значение `0` снимает ограничение.

### Перезагрузка контроллера во время прогона

- **Штатная перезагрузка** (`reboot`, из веб-интерфейса): systemd посылает воркеру SIGTERM, это равносильно `stop --now`. Запись прошивки прерывается между блоками, запись загрузчика дописывается: юнит ждёт до 10 минут. Отчёт сохраняется, прерванные устройства получают статус `interrupted:<стадия>:signal`. Во время выключения ОС `wb-mqtt-serial` не запускается (systemd не даёт), это нормально — он стартует при загрузке. После загрузки: `uwb-fw-update update --resume <run-id>`.
- **Пропало питание или сработал watchdog:** воркер исчезает без отчёта.
  - `wb-mqtt-serial` не отключался, а только останавливался, поэтому при загрузке он запускается как обычно.
  - Прогон остаётся в состоянии `running`. Утилита понимает, что он из прошлой загрузки: сверяет `boot_id` ОС и проверяет, что под сохранённым pid действительно воркер.
  - Следующий `update` / `check` / `recover` выведет предупреждение и сам добавит устройства, которые прошивались в момент сбоя.
- **Устройство, чья прошивка была прервана,** остаётся в загрузчике без рабочей прошивки. Его опрос в `wb-mqtt-serial` будет с ошибками, пока не выполнить `uwb-fw-update recover` (или `update --resume`). Автоматически после загрузки восстановление не запускается.
- **Обрыв передачи загрузчика не должен повредить устройство,** если у самого устройства не пропадало питание: передача незавершённого загрузчика не запускает его перезапись. Опасно только пропадание питания **устройства** в момент перезаписи. Это вывод из описания протокола, на железе не проверялся.

Продолжить остановленный или прерванный прогон:

```sh
uwb-fw-update update --resume <run-id>        # отменённые, прерванные и незавершённые устройства
uwb-fw-update recover --from-run <run-id>     # только восстановление
uwb-fw-update runs                            # список прогонов
```

## Как обновляется одно устройство

1. **probe.** Читаются регистры: 128 — адрес, 290 — сигнатура, 250 — прошивка, 330 — загрузчик, 200 — модель.
   - Не отвечает → проверяется, не в загрузчике ли оно: на рабочих настройках, затем (только локальный порт) на 9600 8N2.
   - Отвечает, но регистра 128 или сигнатуры нет (ОВЕН PR200, вентустановки и другое стороннее оборудование) → `skipped:foreign`. **Такие устройства только читаются: в их регистры ничего не пишется.** Проверено на железе: к каждому стороннему устройству уходит два кадра чтения и ни одной записи. Пробная запись для поиска загрузчика выполняется, только если устройство полностью молчит, отдало сигнатуру WB или уже известно как WB по `devices.json`.
2. **plan.** Целевые версии берутся из индекса релиза. Загрузчик обновляется, только если в кэше есть **и** загрузчик, **и** прошивка.
3. **jump.** Переход в загрузчик:
   - через рег. 131 с сохранением настроек порта (загрузчик ≥ 1.3.0, при чётности ≠ N — ≥ 1.4.0);
   - иначе через рег. 129 на 9600 8N2 — только на локальном порту или если устройство уже работает на 9600 8N2.

   Через TCP-шлюз скорость линии не переключить, поэтому без поддержки 131 устройство получает `failed:jump:tcp_requires_131_or_9600` и остаётся нетронутым.
4. **flash_bl → flash_fw.** Обновление загрузчика стирает прошивку, поэтому сразу после него записывается прошивка.
5. **verify.** Ожидается старт прошивки (при необходимости — рег. 1004), затем версии сравниваются с целевыми.
6. **recover.** Выполняется при любой ошибке записи или если прошивка не стартовала. Сигнатура читается из загрузчика или берётся из `devices.json`, релизная прошивка записывается повторно (`--recover-attempts`, по умолчанию 2).

## Статусы в отчёте

| статус | значение |
|---|---|
| `updated` | обновлено и проверено |
| `recovered` | было в загрузчике — восстановлено |
| `up_to_date` / `update_available` | актуально / есть обновление (режим `check`) |
| `alive` | режим `recover`: устройство работает, восстанавливать нечего |
| `in_bootloader` | режим `check`: устройство в загрузчике |
| `skipped:<причина>` | `port_disabled`, `device_disabled`, `wbio_module`, `foreign`, `no_release`, `modbus_tcp_unsupported`, `duplicate_slave_id`, … |
| `failed:<стадия>:<причина>` | стадии `probe` / `connect` / `download` / `jump` / `flash_bl` / `flash_fw` / `verify` / `recover`; причины `no_response`, `tcp_requires_131_or_9600`, `signature_mismatch`, `download_error`, `bootloader_lost`, `connection_error`, `unstable_link`, `version_mismatch`, … |
| `stuck_in_bootloader:<причина>` | не удалось восстановить автоматически, нужна ручная работа |
| `interrupted:<стадия>:operator` | прервано `stop --now`; продолжить через `--resume` |
| `cancelled` | не начиналось из-за остановки |

Код выхода: 0 — все устройства в порядке, 1 — есть проблемы, 2 — ошибка параметров, 3 — ошибка окружения (сеть, блокировка, конфиг).

## Кэш

```sh
uwb-fw-update cache sync [--port ...]   # скачать прошивки и загрузчики для известных устройств (после check)
uwb-fw-update cache list | verify       # содержимое и проверка целостности
uwb-fw-update cache prune [--dry-run]   # удалить то, что не нужно текущему релизу
```

Индексы релизов перепроверяются не чаще раза в 10 минут (условный GET). Если сеть недоступна, используется последняя скачанная копия. Файлы прошивок сверяются с md5 при каждом использовании, повреждённые перекачиваются.

## Безопасность и ограничения

- **Обновление загрузчика через шлюз.** Включено по умолчанию. Вики WB рекомендует обновлять загрузчик только при прямом подключении и с резервным питанием: сбой в окне около 100 мс после записи делает устройство неработоспособным. При ненадёжной линии используйте `--no-bootloader`.
- **Одновременные прогоны** запрещены блокировкой `/run/lock/uwb-fw-update.lock`.
- **Требования к шлюзам.** WB-MGE v2 и WB-MIO-E v2 — режим «TCP Server / None». WB-MGE v3 — «прозрачный мост»: он допускает одного мастера, поэтому в режиме `direct` `wb-mqtt-serial` на время прогона останавливается (в режиме `rpc` мастер один — сам драйвер). Порты `modbus tcp` не поддерживаются.
- **Пользовательские данные.** Для WB-MSW и WB-MIR обновление прошивки удаляет сохранённые ИК-команды — сохраните их заранее.
- **Модули WBIO** (`X:N`) отдельно не прошиваются, прошивается сам WB-MIO (адрес `X`).

## Разработка

```sh
python -m unittest discover -s tests -t .
```

Релиз: поднять `__version__` в `uwbfwup/__init__.py`, прогнать тесты, пересобрать и закоммитить `uwb-fw-update`, запушить `main` и выполнить `python tools/release.py` (нужен `gh` с `gh auth login`). Скрипт создаёт тег `v<версия>` и релиз с файлами `uwb-fw-update` и `uwb-fw-update.sha256` — их и находят `version --check` и `self-update`.

Тесты не требуют железа. Режим `rpc` проверяется на фейковом MQTT-брокере с эмуляцией RPC `port/Load` (`tests/fake_broker.py`). Эмулятор устройств реализует прошивку, загрузчик, регистры 129/131/1004, информационный блок и блоки данных, а также внедрение сбоев: обрыв записи, потерю загрузчика, «мёртвую» прошивку, отсутствие ответа.

Источники логики:

- [wb-mcu-fw-updater](https://github.com/wirenboard/wb-mcu-fw-updater): `wb_modbus/bindings.py`, `wb_modbus/instruments.py` (Modbus через RPC `port/Load`), `wb_mcu_fw_updater/fw_flasher.py`;
- [wb-mqtt-serial](https://github.com/wirenboard/wb-mqtt-serial): `src/rpc/rpc_fw_update_task.cpp`, `src/rpc/rpc_port_load_raw_serial_client_task.cpp`;
- [wb-ai-skills](https://github.com/wirenboard/wb-ai-skills): `wb_cli/lib/serial_port.py`, `wb_cli/lib/rpc.py`, `wb_cli/commands/serial/_wb_fw.py`, `wb-plc/skills/wb-serial/references/fast-modbus.md` (RPC `port/Load` без остановки драйвера, `fw-update` wb-device-manager);
- вики: [Обновление прошивок](https://wiki.wirenboard.com/wiki/WB_Modbus_Devices_Firmware_Update), [Bootloader](https://wiki.wirenboard.com/wiki/Bootloader).
